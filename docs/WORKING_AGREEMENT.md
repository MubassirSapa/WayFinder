## Meeting Information

- The team will meet every Monday at 7:00 PM Eastern Time during the CAPSTONE project.
- The regular meeting platform will be Microsoft Teams.
- If the regular meeting time must change for a specific week, the team will confirm the replacement time in advance.
- Additional short meetings may be scheduled when a milestone, Pull Request, blocker, or presentation requires team discussion.
- Team members should arrive prepared with progress updates, blockers, and next steps for their assigned work.

## Communication Expectations

- The team will use Microsoft Teams as the primary communication channel for project updates, meeting coordination, and quick questions.
- GitHub Issues and Pull Requests will be used for work tracking, technical discussion, review feedback, and decisions tied to project changes.
- Team members should respond to project messages within 24 hours on weekdays whenever possible.
- If a team member cannot respond within the expected time, they should notify the team in advance when practical.
- Blockers that may delay an assigned issue, milestone, meeting, or submission must be communicated as early as possible.

## Accountability Rules

- Team members are responsible for completing assigned work by the agreed deadline or communicating risks before the deadline is missed.
- A team member who cannot attend a meeting should notify the team before the meeting and review any notes or action items afterward.
- Repeated missed meetings without notice may result in reassignment of responsibilities and reporting the concern to the professor if the issue continues.
- Repeated lateness may result in the team assigning time-sensitive tasks to members who are available for scheduled collaboration.
- Lack of participation may lead to additional documentation, testing, or project tracking duties so the team can verify contribution and progress.
- Failure to respond to teammates for more than 24 hours during active project work should be followed by a reminder. Continued lack of response may be documented and escalated to the professor.
- Accountability actions should be discussed professionally and recorded clearly when they affect responsibilities or project decisions.

## GitHub Workflow Agreement

### Branching

- The `main` branch represents the shared project baseline.
- Direct pushes to `main` are not allowed except when the team explicitly agrees on an urgent administrative correction.
- Each change should be completed on a separate branch connected to the related task or issue.
- Branch names should be short, clear, and use lowercase words separated by hyphens.

Examples:

- `docs/working-agreement`
- `feature/issue-12-login-page`
- `fix/issue-18-cart-total`

### Pull Requests

- Changes are merged into `main` through Pull Requests.
- Pull Requests should describe the purpose of the change, reference the related Issue when applicable, and explain how the change was verified.
- Each Pull Request should be reviewed by at least one teammate before merging.
- Reviewers should check for correctness, clarity, assignment requirements, testing evidence, and whether the change matches the related Issue or acceptance criteria.
- Review feedback should be addressed before merge unless the team documents why a suggestion is deferred.
- The author should avoid merging a Pull Request while requested changes are still unresolved.

### Issues And Project Tracking

- GitHub Issues will be used to define backlog work as user stories.
- Issues should be assigned to the appropriate milestone when the work belongs to a planned project phase.
- The GitHub Project Board should be updated as work moves through `To Do`, `In Progress`, `Reviewing`, and `Done`.
- Team members should keep issue status and board status accurate enough for the team to understand current progress.

## Testing Requirements

- Before opening a Pull Request, the author must verify that the change works as intended.
- The author should test the acceptance criteria for the related Issue and document relevant verification in the Pull Request.
- Automated tests should be added or updated when the project has an appropriate automated testing setup for the changed behavior.
- Existing automated tests should pass before a code change is merged when those tests are available.
- Documentation changes should be checked for readable Markdown formatting, correct links, clear wording, and GitHub rendering.
- Pull Request reviewers are responsible for checking the testing notes and confirming that the change has enough verification for its risk and scope before approval.

## Decision Making And Conflict Resolution

- The team will aim to make decisions through discussion and agreement.
- When a decision is needed quickly, the Project Lead may choose a direction after considering teammate input and assignment requirements.
- Technical disagreements should be resolved by comparing requirements, project constraints, testing evidence, and maintainability.
- If a collaboration issue cannot be resolved within the team, the team will document the concern and contact the professor for guidance.

## Agreement Review

- This working agreement may be updated as the project changes.
- Updates should be made through the team GitHub workflow so changes remain visible and reviewable.

## Team Declaration

We agree to follow this working agreement and contribute responsibly to the planning, communication, development, testing, and documentation of the project.
