# Changelog

## [Unreleased]

### Added
- Newly signed-up organizations now require platform-admin approval before their owner/team can use the dashboard or map editor. Signing up and verifying email still works as before, but a new `Organizations.approved` field (platform-admin-only) gates real access: an `afterChange` hook emails `ADMIN_EMAIL` for review on signup, and approving in the Payload admin panel syncs a denormalized, JWT-embedded `Users.orgApproved` field onto the org's users and emails the owner. Until approved, signing in redirects to a new `/pending-approval` page (`PrivateLayout`) instead of `/dashboard`/`/editor`, matching the visual style of the other auth pages (`check-email`, `verify-email`) — it names the caller's actual organization rather than generic copy, keeps the support-contact line visually separate from the review message, and offers a sign-out action. The `verify-email` success screen now also mentions the review step and the support email, instead of the old "your account is now active" copy that stopped being true once this gate exists. See `docs/project/SCHEMA.md` and `docs/technical/APPLICATION_ARCHITECTURE.md` for the full breakdown.

### Removed
- The "welcome" email that fired immediately after email verification (`sendOwnerWelcomeEmail`/`WelcomeEmailTemplate`) is gone - it told the owner their workspace was "ready" before the new org-approval gate above existed, which would now be misleading. The equivalent "you're ready, sign in" messaging is sent by the org-approval flow instead, once an admin actually approves.

The dot's color is a neutral grey instead of warning-yellow, which clashed sitting on the button's own green "ready to save" fill.

### Fixed
- Fixed object/node dragging in the map editor committing a move on any pointer movement at all, with no minimum-drag-distance threshold - a plain click to re-select an object or node (mousedown+mouseup with only incidental pixel jitter, which real pointing hardware almost always produces) was enough to snap it to the nearest grid line and re-dirty it, silently discarding a precise value just set from the inspector. `useObjectDrag`'s move/resize cases and `useNodeDrag` now require `DRAG_THRESHOLD` (6px, matching the canvas-pan/floor-resize hooks that already had this guard) of real movement before committing anything.
- The editor canvas's trackpad gestures were both routed through zoom - a two-finger pan was misread as a zoom because the wheel handler never checked `event.ctrlKey`, the browser's own signal that a wheel event is actually a pinch (versus a plain two-finger scroll). Plain scroll now pans (matching Figma/Miro), Ctrl+scroll or pinch still zooms. This also changes a bare mouse wheel from "scroll to zoom" to "scroll to pan," since browsers give no reliable way to tell a mouse wheel apart from a two-finger trackpad scroll.
- A path node's outline in the map editor was set to `var(--editor-background)` - literally the same color as the canvas, so it was invisible by design against a plain floor. Switched to `--editor-border-strong`, the token already used elsewhere for a visible outline that inverts correctly per theme.
- Applied the same wheel pan/zoom fix to the public map viewer's gestures (`useMapViewerViewportGestures`) - it had the identical always-zooms bug.
- Removed the Hallway object's outline entirely (`stroke: 'none'`) after several attempts at a stroke color that stayed distinct from the fill in both themes never landed well enough - fill-only reads more clearly than a border that keeps threatening to blend in.
- What actually made a path edge (the line between two nodes) unclear crossing over an object like Hallway wasn't a color problem - objects rendered *after* edges/nodes in the canvas's SVG, so an object's own fill literally painted over and dimmed anything under it. Reordered the canvas so objects sit at the bottom, path edges above them, and nodes above that. Path edges also got a "casing": a wider `var(--editor-background)`-colored line drawn behind the visual one, the standard technique for keeping route lines legible over any background, in case an edge ever crosses something else in the future.
- Object labels were baked into each object's own render, so they inherited the objects layer's (now bottom-most) z-order and could get covered by an edge/node crossing the shape. Split into a separate `MapObjectLabelLayer`, rendered last so labels always stay on top and readable.
- In "Add Path Nodes" mode, clicking on top of an existing object selected that object instead of placing a node there: `MapObjectView` selected the object (and stopped the click from bubbling) in every non-select mode, and the canvas's own click handler separately ignored any click that didn't land exactly on the SVG/grid background. Both now make an exception for "node" mode, so a click always places a node wherever you click, same as clicking empty canvas.
- An object with more than one associated node (e.g. two entrances into the same room) always routed to/from whichever node happened to come first when searching by array order - regardless of which was actually closer, or which one satisfied "accessible route only" when the other didn't. `findBestNodeIdForObject` now tries every node linked to the object against the route's other known endpoint and keeps whichever produces the shortest valid path, falling back to the first node only when there's nothing yet to compare against (e.g. the very first map click, before any destination exists). Applies to manual search picks, clicking an object on the map, and shared/QR route links (which resolve both endpoints jointly, since either side of that link can itself be a multi-entrance object).
- The public map viewer's header showed the organization's name in the primary breadcrumb slot instead of the building's - swapped to `activeFloor.buildingName` (already loaded, just unused). Renamed the id-prettifying fallback helper from `formatOrganizationName` to `formatIdAsTitle` since it's a generic slug-to-title formatter, not organization-specific - it was already being reused for the building id fallback before this, just under a misleading name.
- Accepting an invite still sent Payload's "verify your email" email, even though the account is marked verified (`_verified: true`) the moment the invite is accepted, since the invite link itself is already proof of ownership of that email address. `_verified: true` only marks the DB record verified - the email send is gated by a separate `disableVerificationEmail` create option, which the invite-accept call never passed. Self-signup is unaffected and still requires the real verification email.
- The public map viewer got visibly janky after a few minutes of use on a floor with a lot of rooms/nodes (e.g. 30+ rooms, 100+ path nodes/edges) - `MapViewerSvg`'s `memo()` (meant to skip re-rendering the whole floor on unrelated interactions) was silently defeated by `MapViewerShell` recreating its `onBackgroundClick`/`onObjectSelect`/`onConnectorActivate` callbacks, and separately by `useMapViewerViewportGestures` recreating the pointer handlers it forwards through as `onPointerDown`/`onPointerMove`/`onPointerUp`, on every single render - so effectively every tap, search keystroke, or store update re-rendered every room/node/edge on the floor regardless of whether anything about the map actually changed. Both are now `useCallback`'d end to end (not a memory leak - none was found; this was pure wasted re-render work that scaled with map size). Verified against a synthetic 30-room/100-node/105-edge fixture, not just a toy case.
- On phone, pinch-to-zoom/drag only worked when the gesture started directly on the rendered floor - the SVG is sized to the floor's own rendered dimensions, not the full viewport, so a touch starting in the empty space around a floor that doesn't fill the screen (zoomed out, or just smaller than the viewport) never reached any handler. Desktop's wheel-zoom never had this problem, since it was already bound to the full-size outer viewport container. Relocated the pointer handlers onto that same container (also fixes the dashboard's QR floor preview, which shares the same stack).
- Jumping to a route segment (e.g. changing floor mid-route) could zoom in far past the normal interactive zoom range - a short segment (two nodes close together, or one collapsing toward a single point) computes a tiny bounding box, and `getFitBoundsView` was reusing the same "always allow this exact zoom, even past the usual range" override `getFitZoom` legitimately needs for making a whole floor fit. A tight route segment isn't a floor - there's no reason it should ever zoom in further than a normal click/pinch could. Now clamped to the regular min/max zoom profile.

### Added

- Added a route breadcrumb to the map canvas's own toolbar: when the active route crosses floors, it replaces the plain floor-name label with a clickable `Floor A > Floor B` trail (each non-active segment jumps to it), giving the same floor-hopping access the sidebar's route stepper has without needing to open it.

### Changed
- Merged the map editor's "Select & Move" and object-placement modes into one: picking an item in the "Add to Map" panel no longer switches into a separate mode that blocks dragging. You can now move/resize/rotate existing objects and double-click to place new ones without switching anything, and this is the default mode. Toolbar label updated to "Select & Place" to match.
- Node labels on the map editor canvas are now hidden by default and only appear on hover or while the node is selected, instead of every node's label being permanently rendered (with dozens of nodes on a floor, that was mostly visual noise). The label field itself is unchanged — still set and stored the same way, just not drawn on the canvas at all times.

Computed entirely from objects already loaded in the editor's local state (a simple count), so it adds no server round trip or database query.

Panel copy was also reworded to be less jargon-heavy (e.g. "Objects" → "Add to Map").
- Removed the toolbar's "Object" mode toggle — it was ~95% identical to "Select & Move" (both let you drag/rotate/resize existing objects) and was never actually needed manually, since picking an item from the "Add to Map" panel already switches into placement mode automatically. Also fixed the overlap itself: "Select & Move" now exclusively handles moving/inspecting what's already on the map, while placement mode (still reachable via the toolbox) no longer lets you drag existing objects or nodes, so nothing gets bumped by accident while you're placing something new. Toolbar buttons now show a hover tooltip explaining what each mode actually does.

### Fixed
- Fixed the public homepage and map viewer header showing a reformatted placeholder like "Building 1" instead of the venue's real Organization name. `buildingId` is a synthetic `"building-" + Organization.id` string with no real "building" collection behind it; both now resolve and display the actual `Organization.name`, falling back to the old formatted placeholder only when it can't be resolved (e.g. no organization assigned).
- Fixed dragging an object in the map editor also panning the whole canvas underneath it. The canvas's click-and-drag panning (added for the editor) listens on `pointerdown`, while object dragging used the older `onMouseDown`; `pointerdown` and `mousedown` are separate native events, so stopping propagation on the object's mouse handler never stopped the pointerdown that fires first and starts a pan. Objects (and non-draggable nodes) now stop the pointerdown too.
- Fixed double-click/double-tap object placement silently doing nothing on trackpad input. The pan handler was capturing the pointer on every press, not just real drags; a captured pointer causes the browser to retarget the compatibility click/dblclick events it synthesizes from touch/trackpad taps to the capturing element instead of whatever was actually under the tap. Capture is now deferred until the drag threshold is actually crossed.
- Fixed a public map viewer bug where searching "Get directions" for a room with no navigation node yet would silently do nothing when clicked — no error, no feedback, the field just stayed empty. Such rooms no longer appear as search results at all, since picking one could never have worked.
- Fixed the map viewer's zoom (scroll/pinch) also triggering the browser's own page zoom at the same time. React attaches wheel listeners as passive by default, which was silently blocking `preventDefault()`; the zoom handler is now a real non-passive native listener, so only the map zooms.
- Fixed truncated room names in the "Get directions" From/To suggestion dropdown — the floor name was squeezed onto the same line as the room name, cutting long names short. Floor name now sits on its own line below.
- Fixed objects on the public map being effectively unclickable on trackpads: pressing a room also reached the map's own pan-drag handler (nothing stopped that pointerdown from bubbling up from the object to the SVG), so any tiny amount of pointer movement between press and release — near-unavoidable on a trackpad — crossed the drag threshold and silently suppressed the click as "that was a pan, not a click."
- Fixed the public map viewer at `/map/[floorId]` listing every published floor across every building/organization on a single floor's page, instead of only the floors belonging to that floor's own building. The floors query had no `buildingId` scoping at all.
- Fixed a hydration mismatch on the theme toggle button: its `aria-label`/`title` depended on the resolved theme, which differs between the server render (no theme context yet) and the client's first paint before `next-themes` settles, causing a React hydration warning. The label is now a neutral "Toggle theme" until mounted, then flips to the theme-specific text.
- Fixed a cross-floor route sometimes revisiting the same floor twice, non-consecutively (e.g. "Ground → 1st → Ground → 2nd"). Stairs/elevator/escalator edges had small flat distances regardless of the floor's actual size, so the shortest-path search could legitimately treat bouncing through another floor and back as "cheaper" than a longer same-floor walk. Crossing a floor now carries an added distance penalty representing real-world effort, so the search only leaves a floor when it's actually worth it.
- Fixed the map viewer's active floor and the active route segment drifting out of sync. Switching floors via the header dropdown or double-clicking a canvas connector updated only the displayed floor, not which route segment was "active" — so an already-found route would stop being drawn, and the header, in-canvas breadcrumb, and route panel could each disagree about the current floor. All floor-changing entry points (header, sidebar, canvas connector jump, route panel row, floor-hop button) now read and write the same state.

Once an origin exists, further clicks just select/inspect as before — you can still change it explicitly.
